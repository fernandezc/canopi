# Stored data after 2.0 migrates forward in frozen steps

Status: Accepted (2026-10-16, Canopi 2.1 target; built by the 2.1 foundation phases); amended 2026-10-17 (Q34 to Q36, Q40, Q47, Q45 pass; ledger 2.1-Q35r, 2.1-Q54, 2.1-Q67, 2.1-Q69, 2.1-Q82, 2.1-Q96, 2.1-Q112, 2.1-E4, 2.1-E6, 2.1-E7, 2.1-M9, 2.1-M15 to 2.1-M17)

## Context

ADR 0021 refused data from before 2.0. In 2.0 every reader refuses any version but the current one, each store's version is a hand-written constant, so a bump without a step compiles, and Web keeps every Draft in one localStorage key that loses Drafts above a few MiB. The `.canopi` rules are 20 hand-written Rust and TS pairs with 13 drifts. The user decided that `.canopi` (2.1-Q6) and every local store (2.1-Q33) migrate forward in chained steps, the spec is generated and frozen (2.1-Q7), Web Drafts move to IndexedDB (2.1-Q8), and one Rust core serves both editions (2.1-Q34).

## Decision

- **One rule for all user work.** From 2.0 on, each release that changes a user-work store's shape ships one frozen vN-1 -> vN step for that store. Steps run in sequence when the store opens; a newer version is refused, unchanged; data from before 2.0 is handled as ADR 0021 says.
- **User work or derived.** User work has a chain: `.canopi` (files, Drafts, stamp files), saved-stamp payloads, the settings record, the user DB tables, the library catalogue, source `meta.json` and the browser records. Derived stores (display COGs, previews, the image cache) have no steps: a bump wipes and rebuilds them.
- **A runner per store.** A store has a floor, its version at the v2.0.0 tag (`.canopi` 9, user DB 9, saved-stamp payload 2, settings 1, catalogue 25, `meta.json` 1, Web record containers 3; a 2.0 settings record has no version field and reads as 1), and an ordered list of steps; the current version is the floor plus the number of steps, so a bump without a step does not compile.
  - Outside `.canopi`'s additions rule below, a change that only adds (an optional field, a nullable column, a table) is still a frozen step that only adds, with its fixture; it never rewrites rows. A stored code id (tool, panel, command) unknown at read is dropped, never refused.
- **One store-open lifecycle:** opening, migrating, then ready, recovered, refused-newer, set-aside-damaged or unavailable (`StoreOpenStatus` in `canopi-types`, one `SubsystemHealth` record from store id to status, read by one model in `failures/`). A migration writes a copy and swaps it in durably once verified. The plant catalog is a read-only row.
- **Degraded stores** (2.1-Q67). A store refused as newer or unavailable is never written for the session: settings run on defaults, user-DB features turn off, each with one notice that says changes are not kept; the library is read-only; the Design stays saveable.
- **Rollback by one release destroys no work** (2.1-E4, 2.1-M9, 2.1-E7). The previous release opens everything as it was saved before the upgrade; what the new release saved stays in its new form, refused or unseen by the previous release and unchanged, until a re-upgrade, where the form written last wins and the form it replaces is kept.
  - Readers ship one release before writers. Where the previous release cannot read the new form, or would drop its fields when it writes (2.0 is released, and its settings and Web readers drop unknown keys), the new form gets a new home and the previous form stays beside it, unchanged and unwritten, for one release. An older native build refuses a newer store unchanged.
  - `.canopi`: the pre-upgrade copy below. Web Drafts: the 2.0 localStorage key, which 2.1 copies and verifies but leaves unwritten until 2.2 removes it.
  - Desktop Drafts (2.1-M15): every v10 Draft is written to `drafts-v10/<id>.canopi`, and `drafts/` stays unwritten for one release, so 2.0 lists every Draft as it was before the upgrade. 2.1 lists both, migrating each `drafts/` Draft that has no v10 form or was written after it, and keeping the replaced v10 file once (2.1-E7); never shown to the user.
  - Native stores: a step 2.0 cannot read, or whose fields 2.0 would drop, writes its result to a new versioned path (`user-v10.db`, `library-v26/`), migrated from a copy; the 2.0 file is left unchanged until the next release deletes it. A re-upgrade migrates again from the previous form when it was written after the new one, so the latest work wins.
  - The library (2.1-M16): 2.0 prunes, at every open, each asset, original and job root its v25 catalogue does not name, so `library-v26/` holds the v26 catalogue and every file 2.1 writes. 2.1 reads v25 files in `lidar/` in place and deletes none while the v25 catalogue is kept; its janitor also keeps what the kept copy names.
  - Kept copy (2.1-E7): every upgrade that replaces a store's current form first keeps that form once beside the store (`user-v10.replaced.db`, the `settings.v2.replaced` row, a `.replaced` Web key), byte-identical, so a rollback, edits in the previous release and a re-upgrade lose no 2.1 edits. The copy is never read by the app, is replaced by the next such upgrade, and is named in the store's open status and the problem report.
  - Web records: settings and every browser record whose shape 2.1 changes move to a new key, and the v3 keys are left for 2.0 tabs, which keep running after the deploy (2.1-Q83); only new keys carry the 2.1 shape. A store still shared with 2.0 gets no new literal in a field 2.0 reads as a closed set.
- **`.canopi` admission** has four typed outcomes: current, before the floor, `Migratable{from}`, newer.
  - A migrated open is clean, so only a real edit writes. Before the first write in a new format on a Desktop file home, the old file is kept once beside it (`Garden (Canopi 2.0).canopi`) and a notice says so; an unwritable folder is named in the notice, which asks before saving (save state `copy-blocked`; 2.1-Q35r). A Web open makes a Draft and leaves the user's file untouched, and a migrated Draft is no user file, so neither shows the notice; a Desktop Draft's v9 form is kept by Rollback.
  - A failing step refuses with `migration_failed{from}`; the file is unchanged, and such a Draft is listed as unreadable. Migration runs once at the one decode choke point, on JSON values checked by the frozen vN-1 schema; every write passes the same admission as a read.
- **One core** (2.1-Q34). `canopi-format` (ADR 0023) owns the `.canopi` read checks, the chain, the writer and its admission, the wire conversion, the new-Design builder, typed refusals, the spec emitter, the Draft summary rule and the saved-stamp payload chain; Desktop runs it natively through executor-backed commands, Web as wasm in one worker. TS keeps the generated types, the adapter, the error mapping and the edit-time predicates.
  - The core also owns (Q45): an unnamed Design stores an empty name; Recent Designs refuse with Open's `DesignLoadFailureKind`; groups are normalised at decode and refused on write when dangling or under two members; unreadable Drafts are listed, never hidden.
- **The spec** (2.1-Q7) is emitted by the core into `canopi-format/spec/v<N>/` (schema, fields, new-Design defaults, a fixture cut from the tag covering every field with a non-default value and one unknown root key, and its hand-written expected output), frozen per release. IPC is not versioned.
- **Additions that keep the version** (2.1-Q36). From v10, an optional field valid alone, at the root or nested, and a new literal of an open set need no step; the release check accepts such a schema diff as `v<N>/additions/`.
- **The v9 -> v10 step** (2.1-Q69) is the only 2.1 `.canopi` bump: ramps, raster quantities and locales become open strings (a reader keeps an unknown literal and uses the documented default); every nested object gains an extension bag that keeps unknown keys; `plant_display` moves out of `extra` into a typed Document field; the budget keeps plants only, each line reduced to its target and unit cost, with one currency per Design (2.1-Q96). 2.0 refuses a v10 file as newer.
- **Saved stamps** are relative arrangements in ground metres (ADR 0001, 2.1-Q78d; a 2.0 payload keeps its numbers, now read as ground metres), not `.canopi` objects. Each payload carries its version (floor 2); its chain is in `canopi-format`, run per row by each edition's stamp store (the user DB on Desktop, a browser record on Web, 2.1-Q112). `SavedObjectStampPayload` lives in `canopi-types`. An exported stamp file is a `.canopi`.
- **Settings** make their first shape change in 2.1 (the unit system, 2.1-Q120). Their chain is data in the settings field table: a step adds a field with its default, renames or drops a field, or maps a literal, and both editions' runners are generated from it, so no step is written by hand in two languages; a step that cannot be data moves the chain into `canopi-format` (2.1-E6). On Desktop the record stays a user-DB row (2.1-M17): 2.1 writes `settings.v2` beside the 2.0 `settings` row, which it leaves unwritten, and N2's `user-v10.db` copy carries both.
  - Boot reads are synchronous on Web only; Desktop reads through a reserved UserData slot. A bad value resets only that field and keeps the rest, the Maps key included; the original record is kept once as `settings.before-reset` (a user-DB row on Desktop; secret, replaced by the next reset, never read by the app); one notice says what was reset, on both editions (2.1-Q54). Writes are patches of changed fields, so a write keeps keys it does not know and never overwrites a newer record.
- **Web Drafts** (2.1-Q8). One IndexedDB record per Draft with its `.canopi` version and a revision, compared and set inside one readwrite transaction; the store takes its `IDBFactory` (2.1-Q47). Persistence is requested on the first Draft with a one-line reason; if refused, the welcome screen and save status warn and offer Download .canopi (2.1-Q82). The first Web step copies every Draft, refused ones included, and verifies each canonical encode. A 2.0 tab writing after the move goes to that id's one "copied from an older tab" Draft, never overwriting the original.
- **An old tab meets a newer database** (2.1-Q40). It saves, closes its connection and shows the one "New version: Reload" notice that a deploy shows (2.1-Q83); the new tab shows `draft_store_blocked` while blocked; an older build refuses a newer store with `draft_store_newer`, shown as the same notice. A pending-write marker found at open names the Draft whose last change may be missing.

## Alternatives rejected

- **Refuse older files after 2.0.** Users lose their own work at each format change.
- **Two hand-mirrored codecs with a parity test.** Every step written and tested twice; the parsers already drifted.
- **One key per Draft in localStorage.** The quota stays shared and small.
- **Setting the whole settings record aside on one bad value** (ADR 0021). It loses the Maps key and every other choice.

## Consequences

- Supersedes [ADR 0003](0003-no-backward-compatibility.md) and [ADR 0013](0013-stored-data-migrations.md), and replaces the after-2.0 parts of [ADR 0021](0021-canopi-2-breaks-stored-data.md). Each format change names its step in the handoff; the scenario re-walk counts a format bump as one owner, the core.

## Checks

- A migration harness, `migration_steps_frozen`, the schema release check, `canopi_format_fixture_covers_every_field` and `no_design_field_holds_library_results` (to be created by Phase 2b); the oracle corpus (exists: `canopi-design-conformance.test.ts` and its Rust twin) run natively and through the real worker, plus round-trip property tests.
- Session scenarios and the Draft-store suite in Chromium, WebKit and Firefox (Phase 2b): the Q35r copy and `copy-blocked`, the Q40 cases, the 2.0 tab after the move, a 2.0 tab writing settings, favourites and recently viewed after the 2.1 deploy, the kept 2.0 key; a settings fixture with one bad field per type (Phase 2e); a model test that no write reaches a degraded store (Phase 1b).
- A rollback fixture test per store step (Phases 2b, 2e, N1, N2; Desktop Drafts in 2b) runs the 2.0 reader on 2.1's output, then writes the 2.0 form and re-upgrades, and finds the replaced 2.1 form kept once beside the store, byte-identical (2.1-E7).
- The D3 rollback test (Phase 4) installs 2.0 over 2.1's stores and names each 2.1 step: `.canopi` v10, Desktop Drafts v10, the Web Drafts move, user DB v10, library v26 holding 2.1 imports and results, settings v2 and each moved Web record; each 2.0 store opens with its pre-upgrade content, every 2.1 library item reopens with its files after the re-upgrade, and a re-upgrade keeps the latest work and the replaced 2.1 form beside it.
